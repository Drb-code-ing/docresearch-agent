# pgvector 与 Milvus 在小型知识库场景下的部署与维护约束比较

状态：partial | 模式：controlled-live

引用经过来源校验；结论是否被原文支持仍需人工核对。

## 发现

- 证据基础范围：快照仅含 3 份资料（pgvector.md、milvus.md、selection.txt），且两份产品资料均自我声明「这是项目自编的演示资料，不是性能测试报告或完整产品文档」，因此以下比较仅限于选型层面的定性表述。 [3] [2] [1]
- 部署与依赖约束（pgvector 侧）：pgvector 被描述为「PostgreSQL 的向量扩展」，已有 PostgreSQL 的小型应用可以在关系数据库中保存向量并组合业务字段过滤与 SQL 查询；对规模较小、关系数据关联较多的知识库，复用 PostgreSQL「可以减少额外运维组件」。资料未给出扩展版本、最低 PostgreSQL 版本、安装步骤或依赖包清单。 [3]
- 部署与依赖约束（Milvus 侧）：Milvus 是「面向向量检索的数据库，支持多种向量索引和标量过滤」；采用独立向量数据库可以让检索容量与业务数据库分别规划，但「也增加部署组件、监控、备份和数据同步的维护工作」。资料未记载是否依赖 etcd/MinIO/Pulsar 等外部组件，也未区分单机版与集群版或容器/Kubernetes 要求。 [2]
- 维护约束对比：两侧资料形成一组对称表述——复用已有 PostgreSQL 可减少额外运维组件，而独立向量数据库会带来部署组件、监控、备份和数据同步方面的额外维护工作。该对比是定性的工作量判断，不包含任何具体运维操作、参数或成本数字。 [3] [2]
- 检索能力与集成约束：pgvector 方案中关键词检索可用 PostgreSQL 全文检索，但「向量召回与关键词召回的结果需要独立融合」，且「中文分词策略需要单独设计」；Milvus 侧仅记载支持多种向量索引与标量过滤，选型时需考虑向量规模、更新频率和查询模式。资料未列出任何具体索引类型或参数。 [3] [2]
- 适用场景判断（选型检查表）：应先确定资料量、向量维度、更新频率、权限过滤和检索质量要求，再评估基础设施；「已有 PostgreSQL、数据量小且关联查询多时，可以先验证 pgvector 的实际效果」；「向量规模增长并需要独立扩展检索容量时，可以评估 Milvus 的维护成本和检索表现」。资料同时提醒，小型知识库是否使用 Milvus 应根据已有基础设施及预期增长判断，不能只因组件功能多就断言一定优于 PostgreSQL 的向量扩展。 [1] [2] [3]
- 性能与成本结论的证据限制：资料明确声明「没有 pgvector 与 Milvus 的同条件性能对比，因此不能报告谁的延迟更低或吞吐量更高」，pgvector 资料亦称「未给出百万向量的延迟、费用或吞吐量」；任何性能优劣、召回率和费用结论都必须来自相同数据与条件下的测试。因此本报告不给出任何延迟、吞吐量或成本数值。 [2] [3] [1]

## 资料缺口

- 没有任何性能基准数据：资料中不含延迟、吞吐量、QPS、召回率、内存占用或费用数字，且明确禁止据此编造量化结论；pgvector 与 Milvus 的同条件性能对比在资料中完全缺失。
- pgvector 侧缺口：未记载扩展版本号、最低 PostgreSQL 版本要求、安装/升级步骤、依赖包清单。
- pgvector 侧缺口：未记载 HNSW/IVFFlat 等索引类型、构建与查询参数（如 m、ef_construction、lists、probes）、内存相关参数（如 maintenance_work_mem）及并行构建等配置约束。
- pgvector 侧缺口：未记载备份策略、升级路径、监控指标与调优参数等具体运维条目（仅有『减少额外运维组件』的定性表述）。
- Milvus 侧缺口：未记载 etcd/MinIO/Pulsar 等外部组件依赖、standalone 与 cluster 的区分、容器化/Kubernetes 部署要求。
- Milvus 侧缺口：未记载具体索引类型与参数配置、内存/硬件资源要求、版本升级（含滚动升级）约束。
- Milvus 侧缺口：扩缩容仅有『检索容量与业务数据库分别规划』的概念性表述，未记载具体机制与操作。
- 规模阈值缺口：资料未给出任何量化规模界限（向量数量、维度、QPS），『规模较小』与『向量规模增长』均无具体数值定义；且快照仅 3 份自编演示资料，非完整产品文档，无法覆盖上述主题。
