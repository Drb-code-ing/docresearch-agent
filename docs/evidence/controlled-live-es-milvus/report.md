# pgvector 与 Milvus 小型知识库适用性对比（仅依据自编资料）

状态：partial | 模式：live

引用经过来源校验；结论是否被原文支持仍需人工核对。

## 发现

- 资料性质：三份文档均为项目自编演示资料，非性能测试报告或完整产品文档。pgvector.md 与 milvus.md 均声明“这是项目自编的演示资料，不是性能测试报告或完整产品文档。” [3] [2]
- 部署维护（Milvus）：独立向量数据库“可以让检索容量与业务数据库分别规划，但也增加部署组件、监控、备份和数据同步的维护工作。”即扩展解耦换来更高的运维负担。 [2]
- 部署维护（pgvector）：pgvector 是 PostgreSQL 的向量扩展，“已有 PostgreSQL 的小型应用可以在关系数据库中保存向量，并组合业务字段过滤与 SQL 查询。”且“对规模较小、关系数据关联较多的知识库，复用 PostgreSQL 可以减少额外运维组件。” [3]
- 小型知识库选型原则：“对一个小型知识库，是否使用 Milvus 应根据已有基础设施及预期增长判断。不能只因组件功能多就断言一定优于 PostgreSQL 的向量扩展。” [2]
- 选型路径（检查表）：已有 PostgreSQL、数据量小且关联查询多时先验证 pgvector 实际效果；“向量规模增长并需要独立扩展检索容量时，可以评估 Milvus 的维护成本和检索表现。”前置条件为“先确定资料量、向量维度、更新频率、权限过滤和检索质量要求，再评估基础设施。” [1]
- 检索能力（向量索引与标量过滤）：Milvus“支持多种向量索引和标量过滤。选型时需要考虑向量规模、更新频率和查询模式。”；pgvector 可“组合业务字段过滤与 SQL 查询”。两者均提及向量索引与标量/业务字段过滤，但资料未给出具体索引类型清单或同条件对比。 [2] [3]
- 检索能力（关键词/全文、融合与中文）：“关键词检索可以使用 PostgreSQL 全文检索，向量召回与关键词召回的结果需要独立融合。中文分词策略需要单独设计。”资料对 Milvus 的全文/关键词与中文分词能力无对应说明。 [3]
- 所有量化结论均被原文限制：pgvector.md“本资料未给出百万向量的延迟、费用或吞吐量，不能据此编造量化结论。”；milvus.md“本资料没有 pgvector 与 Milvus 的同条件性能对比，因此不能报告谁的延迟更低或吞吐量更高。”；selection.txt“任何性能优劣、召回率和费用结论，都必须来自相同数据与条件下的测试。” [3] [2] [1]

## 资料缺口

- 无任何性能数字：无延迟、吞吐量、QPS、内存数据（pgvector.md 明确“本资料未给出百万向量的延迟、费用或吞吐量”）。
- 无任何费用/成本数字（部署成本、运维人力、硬件规格均未给出）。
- 无召回率或精度数字，且明确缺少 pgvector 与 Milvus 的同条件性能对比（milvus.md）。
- 索引与检索细节缺口：未给出具体索引类型/参数（如 HNSW、IVF、PQ）、构建与更新维护成本，未说明标量过滤与向量检索的组合方式（先过滤/后过滤），也未给出召回融合算法（如 RRF、加权求和）。
- 中文/全文能力缺口：仅指出中文分词“需要单独设计”，未给出分词器/词典/集成方案；Milvus 侧中文与全文检索能力在资料中完全缺失。
- “小型知识库”缺乏量化边界（资料量级、维度上限、QPS 阈值），也未给出切换到 Milvus 的容量/成本临界点。
- 监控/备份/数据同步仅有定性描述（“增加…监控、备份和数据同步的维护工作”），未给出工具、频率、RPO/RTO、同步延迟或一致性方案；亦未涉及权限过滤/多租户隔离实现细节。
- 资料为自编演示材料而非完整产品文档，上述结论仅在该资料范围内成立，不能外推为产品事实或采购依据。
