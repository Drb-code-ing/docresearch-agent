# pgvector 与 Milvus 对小型知识库适用性：基于给定资料的比较（含资料缺口）

状态：partial | 模式：live

引用经过来源校验；结论是否被原文支持仍需人工核对。

## 发现

- 资料范围界定：两份产品资料均自述为「项目自编的演示资料，不是性能测试报告或完整产品文档」，因此本文所有结论仅限这三份资料所载内容，不构成完整产品对比。 [2] [3]
- 【部署维护·pgvector】原文：「pgvector 是 PostgreSQL 的向量扩展。已有 PostgreSQL 的小型应用可以在关系数据库中保存向量，并组合业务字段过滤与 SQL 查询。」即资料把 pgvector 定位为复用既有 PostgreSQL 的扩展，向量与业务数据同库保存。 [3]
- 【部署维护·pgvector】原文：「对规模较小、关系数据关联较多的知识库，复用 PostgreSQL 可以减少额外运维组件。」即资料把「减少额外运维组件」的收益限定在「规模较小、关系数据关联较多」且已复用 PostgreSQL 的前提上。 [3]
- 【部署维护·Milvus】原文：「采用独立向量数据库可以让检索容量与业务数据库分别规划，但也增加部署组件、监控、备份和数据同步的维护工作。」即资料把 Milvus 定位为独立向量数据库，收益是检索容量可单独规划，代价是部署组件、监控、备份、数据同步的额外维护工作。 [2]
- 【适用性判断·小型知识库】原文：「对一个小型知识库，是否使用 Milvus 应根据已有基础设施及预期增长判断。不能只因组件功能多就断言一定优于 PostgreSQL 的向量扩展。」即资料明确反对仅凭功能数量判定 Milvus 更优。 [2]
- 【检索能力·Milvus】原文：「Milvus 是面向向量检索的数据库，支持多种向量索引和标量过滤。选型时需要考虑向量规模、更新频率和查询模式。」资料仅作此概括性描述，未列举具体索引类型。 [2]
- 【检索能力·pgvector 混合检索】原文：「关键词检索可以使用 PostgreSQL 全文检索，向量召回与关键词召回的结果需要独立融合。中文分词策略需要单独设计。」即资料指出 pgvector 侧的关键词检索依赖 PostgreSQL 全文检索，两路召回需自行融合，中文分词需单独设计。 [3]
- 【选型流程与结论纪律】原文：「先确定资料量、向量维度、更新频率、权限过滤和检索质量要求，再评估基础设施。」「已有 PostgreSQL、数据量小且关联查询多时，可以先验证 pgvector 的实际效果。」「向量规模增长并需要独立扩展检索容量时，可以评估 Milvus 的维护成本和检索表现。」「任何性能优劣、召回率和费用结论，都必须来自相同数据与条件下的测试。」资料（milvus.md）亦载：「本资料没有 pgvector 与 Milvus 的同条件性能对比，因此不能报告谁的延迟更低或吞吐量更高。」 [1] [2]

## 资料缺口

- 规模数据缺口：资料未给出适用于「小型知识库」的任何向量数量、文档量或维度阈值，也未说明「规模较小」与「向量规模增长」的具体分界，无法据此量化判定两种方案各自适用的规模区间。
- 性能数据缺口：资料明确「本资料未给出百万向量的延迟、费用或吞吐量，不能据此编造量化结论」，且「本资料没有 pgvector 与 Milvus 的同条件性能对比」，故无延迟、吞吐量、QPS 或召回率等任何数值可用。
- 成本数据缺口：资料未提供 pgvector 或 Milvus 的任何费用、许可或总拥有成本数据；未给出硬件规格或资源占用（CPU/内存/磁盘）原文。
- 部署细节缺口：资料未提供两者的安装、配置、编排方式（容器/集群/节点角色），也未说明 Milvus 的组件构成与其独立部署的具体形态；pgvector 的执行步骤亦未提供。
- 运维细节缺口：资料仅笼统提及独立向量数据库带来「部署组件、监控、备份和数据同步的维护工作」，未给出监控指标、备份策略、数据同步或升级的具体方案；pgvector 侧亦未展开运维操作。
- 检索能力细节缺口：资料未提及任何具体索引类型（如 HNSW/IVF/PQ 等），未提及距离/相似度度量（如 L2/内积/余弦），未提及一致性级别或读写可见性，未提及维度上限、索引参数、top-k 等查询参数。
- 过滤与权限缺口：资料仅称 pgvector 可「组合业务字段过滤与 SQL 查询」、Milvus 支持「标量过滤」，未说明权限过滤（ACL）的实现方式、混合检索的具体融合算法或加权策略。
- 中文检索缺口：资料仅提示「中文分词策略需要单独设计」，未给出分词方案、检索效果或相关测试数据。
