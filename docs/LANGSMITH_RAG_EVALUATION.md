# 用 LangSmith 理解 RAG 量化评估：从 DocResearch 到面试回答

你已经能解释“检索、重排、补查、生成”怎么运行，接下来还要回答一个问题：**加了这些步骤，答案真的更好了吗？**

LangSmith 的价值不是给技术栈再加一个名字，而是帮助你用同一组问题重复比较，并找到效果变差的具体原因。

本文结合学习仓库的 `2e6d82a` 提交和 DocResearch 的真实结构讲解。学习仓库已编写 LangSmith + OpenEvals 评估示例；本文为 DocResearch 定义评估方案，**没有给本项目接入 SDK、执行新实验或产生质量提升数据**。下面的资料、评分示意和实验分组均用于理解方法，不是实测结论。

## 1. 先把“离线”这个容易误解的词说清楚

**离线评估不等于断网，也不等于使用本地模型。**

它指的是：准备一组固定问题，在实验中批量运行系统并打分，不依赖正在发生的真实用户请求。过程中完全可以调用云端生成模型、评委模型，并把实验记录上传到 LangSmith。

在线评估则面向实际使用中的请求，例如抽取用户当天的问答评分，观察质量是否下降。两者都可以用 LangSmith；区别是评估对象和触发方式，不是有没有网络。

本文说“固定测试集评估”，就是前一种。简历也使用这个更直白的说法。

## 2. 用一道题看懂：为什么一个分数不够

假设用户问：

> 对已经使用 PostgreSQL 的小团队，pgvector 和 Milvus 的部署维护有什么区别？能否确定哪一个每月便宜 30%？

为便于演示，假设资料只包含：

- 片段 A：pgvector 是 PostgreSQL 扩展，可沿用已有数据库的部分管理流程。
- 片段 B：Milvus 是独立的向量数据库服务，需要按部署方式管理相应服务组件。
- 两份资料都没有相同负载下的费用测试。

这是教学设定，不是对具体部署成本的测量。理想回答应当比较部署方式，同时说明：缺少规模、负载、资源配置和费用数据，不能确认“便宜 30%”。

| 发生了什么 | 问题出在哪里 | 该看什么 |
| --- | --- | --- |
| 只找回一篇 PostgreSQL SQL 语法教程 | 没找到回答问题需要的资料 | 检索相关性、带人工标签的召回指标 |
| 找回 A、B，却说“pgvector 每月便宜 30%” | 答案添加了资料没有支持的结论 | 回答忠实度 |
| 找回 A、B，答案只说“两者都是数据库” | 没明显编造，但没有完成比较 | 回答帮助性 |
| 比较部署方式，并明确费用信息不足 | 回答了能回答的部分，也保留了缺口 | 三项指标共同观察，再人工复核 |

所以，“程序没报错”“引用 ID 合法”“评委给了高分”是三件不同的事，也都不能单独证明答案正确。

## 3. 你最新的学习代码究竟做了什么

把代码里的名字翻译成一次考试：

| 名称 | 白话含义 | 学习代码中的对应内容 |
| --- | --- | --- |
| Dataset | 一套试题 | `rag_eval_v1`，定义了 12 条问题及参考答案 |
| Example | 其中一道题 | `inputs.question` 与参考 `outputs.answer` |
| Target | 接受考试的程序 | `runRagAgent(inputs)`，内部调用 RAG 的 `ask()` |
| Target outputs | 程序这次交的答案 | `{ answer, context }`，context 是检索段落文本数组 |
| Evaluator | 按规则评分的函数 | 三个 OpenEvals `createLLMAsJudge` 评估器 |
| Experiment | 某套配置完成整套题的记录 | `evaluate(...)` 指定数据集、评估器和实验名前缀 |

```text
Dataset 中取一道 question
        |
        v
Target: Milvus 检索 -> 生成回答
        |
        v
outputs: answer + context
        |
        +--> 检索相关性评委
        +--> 回答忠实度评委
        +--> 回答帮助性评委
        |
        v
实验记录：本题输出、各项评分与评语
```

学习示例中，Milvus 检索取 `k=4`，LangGraph 编排 `retrieve -> generate`；`evaluate` 的 `maxConcurrency=2` 控制评估样例的并发数。它不是 DocResearch 的子 Agent 并发限制，两者不要混讲。

**最容易说错的地方：数据集有参考答案，不代表评委真的使用了参考答案。**

当前三个 evaluator 没有接收 `referenceOutputs`。其中的 `outputs.answer` 是 Target 当次生成的答案，不是 Dataset 保存的标准答案。是否做“答案与参考答案比较”，取决于评估函数实际拿了哪些参数，而不是数据集有没有那个字段。

这些代码说明你已经编写评估练习。提交里没有实验链接、分数导出或运行日志，因此本文不把“定义了 12 条样例”写成“已成功上传并完成 12 题实验”。

## 4. 三个指标分别看哪两样东西

### 4.1 检索相关性：问题与找回的资料是否有关

输入是 **question + context**。

例如，问题在问部署维护，找回的段落却全是 SQL 函数用法，即使都出现 PostgreSQL，也不算很好地服务这个问题。

学习代码使用 `RAG_RETRIEVAL_RELEVANCE_PROMPT`，将问题放入 `inputs`，将检索文本放入 `context.documents`。

它不自动等于 Recall@K。评委只能评价“送给它的片段是否相关”，不知道资料库里还有多少相关片段没有找回来。要测遗漏多少，必须另外标注应命中的证据集合。

### 4.2 回答忠实度：答案是否有给定资料支持

输入是 **answer + context**。

如果 A、B 都没有费用数据，答案却给出“便宜 30%”，忠实度应当受到质疑。即使引用的是存在的 Source ID，也不能替这个数字提供依据。

学习代码使用 `RAG_GROUNDEDNESS_PROMPT`，feedback key 拼为 `rag_groundness`。名称拼写不影响你应解释的概念：看结论能不能由给定材料支持。

忠实度也不等于现实世界中的正确性。如果资料本身过时，回答忠实复述它，仍可能不符合现实。因此还需要可靠资料、版本信息，必要时加入参考答案正确性评估。

### 4.3 回答帮助性：答案有没有回应用户要解决的问题

输入是 **question + answer**。

“两者都是数据库”可能没有明显事实错误，却没有回答部署维护的区别。反过来，一段写得流畅、建议很多的答案可能看起来很有帮助，却夹带没有出处的数字。

学习代码使用 `RAG_HELPFULNESS_PROMPT`，没有传入原始检索资料或参考答案，不能指望它替代忠实度检查。

对资料不足的题，帮助性标准还应允许“说明已知内容 + 指出缺失信息”，而不是强迫模型给确定答案。DocResearch 的 `gaps` 应当在这里得到合理评价。

### 4.4 三项分数怎么使用

不要先把三个分数相加成“总准确率”。先逐项看，再回到具体坏例子：

- 相关性低：检查查询、分词、召回和重排。
- 相关性尚可、忠实度低：检查模型是否越过证据下结论。
- 忠实度尚可、帮助性低：检查问题是否被答全、比较维度是否遗漏。

评委给的是按某套提示词产生的判断，不是统计意义上的“答案为真的概率”。即使评分区间是 0 到 1，0.9 也不能直接写成“90% 正确率”。

## 5. 放到 DocResearch，应该评哪一段

DocResearch 有外层工具循环、内部 AgenticSearch 和可选子任务，需要分清评估范围。

### 5.1 第一层：基础检索器有没有找对文档

输入问题，调用 `PersistentRetriever.search()`，检查返回的 Source。

项目已有 [evaluation.py](../src/docresearch/evaluation.py) 和 [retrieval_cases.json](../examples/retrieval_cases.json)。这套小测调用检索后端，不调用聊天生成，也不经过完整 AgenticSearch。

现有 `mean_document_recall_at_2` 的确切含义是：**先取前 2 个片段，再把片段路径去重，算命中了多少应命中的文档。** 不是先取前 2 个不同文档。

例如，本题应命中 `{pgvector.md, milvus.md}`，两个返回片段都来自 `pgvector.md`，文档召回就是 `1 / 2 = 0.5`。有答案题逐题计算后再取平均；没有目标文档的题不混入这个分母。

现有无答案指标是“检索是否返回空列表”。它不等于回答是否恰当拒答：检索器可能返回相关背景，但背景不足以证明题目中的费用结论。

### 5.2 第二层：AgenticSearch 是否提供了更有用的证据

评估对象是 [AgenticSearch.search](../src/docresearch/agentic.py)，覆盖：

```text
原问题与查询改写
    -> ES / Milvus 召回与 RRF
    -> 可选专用重排
    -> 证据充分性判断
    -> 必要时最多再查一次
    -> sources / sufficient / missing / attempts
```

这一层主要评检索相关性、证据覆盖，以及资料不足时的判断。这里尚未生成最终报告，不能把内部 `sufficient=true` 当作回答质量得分。

**内部证据判断与外部量化评估的区别：** 前者是执行程序的一部分，决定接下来要不要补查；后者在固定测试条件下检查这些决策有没有帮助。不能让程序自己的 `sufficient` 直接充当唯一的考试成绩。

### 5.3 第三层：整份研究报告有没有完成任务

评估对象是 [ResearchRun](../src/docresearch/runtime.py) 的完整执行：主 Agent 决策，必要时派发子任务，最后保存报告。

这一层评价最终回答的忠实度、帮助性、资料缺口表达，并同时记录运行失败、请求次数和耗时。

简单题和复杂题要分组。否则，一组简单问题的高分不能说明多 Agent 分工有价值；一次并行运行成功也不能说明比单 Agent 更好。

## 6. 评估需要的数据从哪里来

不要求把项目重写成 LangChain。LangSmith 评估所需要的是一个可调用的 Target，以及可以明确解释的输入输出。**语言或框架不是评估边界，输入输出契约才是。**

对 DocResearch，建议把每个测试结果整理成下面的概念结构。这是字段设计，不是仓库中已经存在的接口：

```text
question                  原问题
answer                    最终报告的结论与 gaps
cited_contexts            报告引用的原文
retrieved_contexts        每次 search 实际返回给相应 Agent 的片段
direct_read_contexts      read_source / read_file(corpus) 实际读到的原文
task_results              子 Agent 返回给主 Agent 的结构化结论
run_status                执行状态，不能仅按是否退出成功判断质量
usage                     请求数、可用的 token 统计和耗时
config                    资料版本、模型、提示词及检索配置
```

这些字段为什么不能统称一个 `context`？因为多 Agent 看见的内容不同，评估问题也不同。

| 想回答的问题 | 应当拿什么资料评 |
| --- | --- |
| 每次 search 返回得好不好 | 该次 search 的完整返回片段，包括后来没有被引用的片段 |
| 最终报告的引用是否支持结论 | 报告结论与它实际引用的原文，按结论逐条核对 |
| 子 Agent 有没有基于自己看到的资料作答 | 该子的输出与该子实际读到的证据 |
| 主 Agent 为什么这么总结 | 主实际收到的工具结果、子结果与主自己读取的资料 |

当前落盘文件能提供部分材料：

- `report.md`：最终报告。
- `sources.json`：报告引用的原文快照，可以支持最终引用忠实度分析。
- `tasks.json`：任务依赖和限长子结果，可以帮助定位哪一个子结论出了问题。
- `run.json`、`trace.json`：运行统计和事件，可用于定位失败与阶段耗时。

**但 `sources.json` 不是完整召回日志，`trace.json` 也没有保存所有完整对话与工具正文。** 只评最后引用的片段，会漏掉检索曾经返回的大量无关内容，造成选择偏差。因此，完整检索评估需要在评估适配层捕获真实返回值；本文只定义这个要求，没有把现有文件说成完整追踪。

这也能回答之前关于 Corpus 的疑问：Corpus 保存本次运行的原文与 Source 映射；检索负责找出相关片段；`read_file` 可以补读已知文件。**不能为了方便评分，就把整个 Corpus 塞给评委，假装这些资料全被 Agent 看见过。**

对报告引用作事后核验时，可以让评委读取子结论关联的原文，但要标为“引用支持性核验”，不能说主 Agent 当时也读过它们。

## 7. 怎样做一场有意义的对照实验

### 第一步：准备题目，而不是只挑好答的题

可以先人工写一小批，再逐步扩充。至少覆盖：

| 类型 | 例子 | 主要观察 |
| --- | --- | --- |
| 精确术语 | 哪份资料说明了 HNSW 参数 | 关键词召回 |
| 同义表达 | 不直接写“备份”，而问故障后如何恢复 | 语义召回 |
| 跨文档比较 | 比较两种方案的部署维护 | 证据是否覆盖双方 |
| 信息不足 | 谁每月便宜 30%，但资料没费用 | 是否承认缺口、避免编造 |
| 冲突或过期资料 | 两份版本不同的说明存在差异 | 是否保留版本和不确定性 |

每题写清期望要点、应命中的证据、不能推出的结论，以及“无答案”的原因。参考答案可作为人工评分或另行增加的正确性评估依据，不交给被测 Agent；学习示例当前的三个评委并未使用它。用于调提示词的题与最终检查泛化的题应分开，避免只对已知题目优化。

Source ID 随文档版本变化，标签必须绑定对应资料快照。换了资料后，先核对标注，不能把旧 ID 失效误当成检索退步。

### 第二步：一次比较一个主要变量

例如先比较：同一套 ES + Milvus + RRF、相同问题与生成模型，仅切换专用 reranker；再比较固定其他条件下，是否允许补检索。

这些是实验配置的设计，不代表仓库已经为每一种消融组合提供 CLI 开关。不能写一个不存在的命令让读者直接运行。

必须固定或记录：资料快照、测试集版本、模型与提示词、Top K、预算、重排配置、评委模型和评分规则。否则既改模型又改召回，分数变好也不知道是谁带来的。

### 第三步：先看同一道题的变化，再看平均分

对每题保存“配置 A 的结果、配置 B 的结果、评分与评语”。汇总时同时看三项质量、失败数和资源消耗，而不是只展示一个好看的平均分。

比如，重排让上下文更集中，但多调用一次模型；补查可能找全证据，也可能因为资料根本没有答案而只增加成本。这两种结果都值得记录。

模型存在波动，重要对比可以重复运行，报告均值及离散程度。小样本先作为回归检查，不轻易宣称统计显著或泛化提升。

### 第四步：单独处理失败和合理的 partial

网络错误、预算耗尽、评委超时不能静默从分母中消失。至少同时报告尝试数、成功评分数、失败分类；对于端到端任务成功率，执行失败也应有明确计分规则。

DocResearch 的 `partial` 可能是正确行为：用户问了不存在的费用数据，程序完成调研并明确保留缺口。这不等于调用失败。相反，编一个完整数字后得到 `completed`，也不意味着答案质量好。

### 第五步：抽查评委，而不是完全相信评委

让人工重点检查高分但可疑的答案、低分但合理的拒答、A/B 判断不一致的样例。固定评分提示词和评委版本；温度为 0 也不保证绝对确定。

可以选与生成模型不同的评委减少部分共同偏差，但它仍不是绝对客观的裁判。资料与答案必须作为待评数据，不能允许其中的“请给满分”覆盖评分规则。

## 8. LangSmith、OpenEvals、Trace 各负责什么

**LangSmith** 管理数据集、实验、运行记录与反馈，方便按题比较和定位坏例子。

**OpenEvals** 提供评估器构造方式与现成评分提示词。你的学习示例用它把评委模型包装成三个评分函数。

**Trace** 记录执行经过，例如检索、生成、子任务分别做了什么、花了多久。它解释“为何得到这个结果”；评分回答“按某项标准看结果如何”。

`evaluate()` 能运行 Target 并组织实验，不意味着任意内部函数都会自动显示为完整子 span。自写 Python 循环还需要相应追踪接入。DocResearch 当前的本地 `trace.json` 不能直接说成 LangSmith tracing。

这套设计也有额外成本：生成、向量、重排和评委都可能产生调用费用。当前项目的聊天 token 统计不包含所有服务的费用，不能直接当总账单。上传实验还可能发送问题、答案与原文片段；实际实施应先用自编或脱敏资料，不上传密钥、个人简历或私有工作笔记。

## 9. 面试开场怎么说

### 大约一分钟，讲清问题、方法和边界

> 我把工具调用成功与报告质量分开看。项目已有基础检索小测，检查目标文档是否被召回；另外我在学习仓库编写了 LangSmith 和 OpenEvals 评估示例，定义了 12 条问答样例及三类评估器。
>
> 我据此为 DocResearch 设计固定测试集评估：用检索相关性检查资料是否对题，用忠实度检查结论有无依据，用帮助性检查是否回应了问题，再用同题集对照重排、补查的效果与开销。
>
> 这里完成的是评估方案设计，LangSmith 尚未接入 DocResearch，没有这个项目的实验成绩，因此我不会报未经验证的准确率提升。

这个回答的重点不是“我认识三个英文名”，而是你知道如何判断一次架构改动值不值得。

## 10. 面试官继续追问，怎么接

### 问：为什么不能只看正确率？

> 因为坏答案可能来自不同模块。只看最终分数，我不知道该改检索还是生成。而且当前三个评委不使用标准答案，不能把它们的连续评分叫正确率。我会先分项定位，再对有参考答案的题增加独立的正确性评估。

### 问：有参考答案，为什么你说没有评正确性？

> 我看过 evaluator 的参数，当前只传了问题、生成答案和检索文本中的相应组合，没有使用 `referenceOutputs`。数据放在 Dataset 里不代表自动参加评分。要评正确性，需要另外定义比较参考答案与实际答案的规则。

### 问：忠实度高，是不是就没有幻觉？

> 不能这样保证。它只说明某个评委认为答案受给定资料支持，还可能误判；资料本身也可能有错。我会结合逐条引用核验、版本检查和人工抽查，不把单项评分当事实证明。

### 问：检索相关性和 Recall@K 有什么区别？

> 相关性评委看返回的片段是否对题；Recall@K 要有人工标注的相关集合，计算前 K 个结果覆盖了多少目标。返回的两段都相关，仍可能漏掉另一份关键资料，所以两种指标可以互补。

### 问：项目里的 evidence grade 不就是评估吗？

> 它是检索流程里的决策，决定资料是否足够、要不要补查。外部评估是用固定题目检查这个策略有没有改善结果。执行程序不能只用自己的判断给自己打分。

### 问：你不用 LangChain，为什么能谈 LangSmith？

> 核心是提供可调用的 Target，把问题传给项目，再整理答案、证据和状态给评估器，不需要重写 Agent Loop。内部详细追踪是另一层接入，不能因为用了 evaluate 就宣称每个子调用都自动可见。

### 问：多 Agent 的 context 取什么？

> 要看评谁。评子 Agent 就用它实际读取的证据；评主 Agent 的决策就用主实际收到的结果；评最终引用支持性可以回看关联原文，但不冒充主当时读过原文。不能把全库资料混成一个 context，否则会掩盖没检索到或没传递到的信息。

### 问：怎么证明 Rerank 或补查有用？

> 同一组题、同一份资料和相同模型，做只改变目标机制的对照，逐题看质量差异，同时记录失败、请求次数和延迟。不能把更换模型带来的提升归到 Rerank，也不能只选变好的题。

### 问：你实际上完成到哪一步？

> 学习仓库写了数据集构建、RAG Target、三个 LLM-as-judge 评估器和批量 evaluate 调用。DocResearch 有自己的基础检索小测，我补充了固定测试集与分层评估方案，但没有接入 LangSmith SDK，也没有这个项目的 LangSmith 实验成绩。

### 问：这是不是只加了一个平台名称？

> 不是只列工具名。我能明确每个评委的输入、什么错误会让它扣分、现有报告文件缺了哪些评估数据，以及怎样设计公平对照。但方案设计和接入运行是两种完成度，我会把它们说清楚。

## 11. 简历怎么写才和实际经历一致

个人技术栈可以增加：**LangSmith / OpenEvals（RAG 评估实践）**。这对应学习仓库的真实代码，不需要把它伪装成 DocResearch 的运行依赖。

DocResearch 项目新增的表述为：

> **量化评估设计：** 基于 LangSmith / OpenEvals 设计固定测试集评估方案，定义检索相关性、回答忠实度与帮助性指标，以及重排、补检索的同题集对照方法。

这里的动词是“设计”，不是“上线”“接入完成”或“提升”。有方案、理解方案、能解释取舍，本身就是可以谈的工作；没有必要给它加一个不存在的结果。

以下表述不要用：“LangSmith 测得准确率 95%”“通过评估消除幻觉”“Rerank 提升 20%”“项目已经具备线上质量监控”。目前没有相应证据。

## 12. 看懂了没有，用三分钟自测

1. 资料里没有费用数字，答案给出“便宜 30%”：哪个指标应该发现问题？为什么引用 ID 合法也没用？
2. 找回的两段都来自 pgvector，而应命中 pgvector 和 Milvus：项目现有文档召回是多少？为什么相关性可能仍然不低？
3. 能不能只拿 `sources.json` 评价完整检索质量？漏掉了什么？
4. Dataset 中存在参考答案，如何从 evaluator 代码判断它是否真的参与评分？
5. 为什么合理地保留资料缺口，不应该与 API 调用失败混在一起？

参考思路：忠实度与语义支持；前两个片段的文档覆盖为一半；仅引用资料会遗漏未引用召回；检查 `referenceOutputs` 是否传入并使用；任务完成度与证据可回答性是不同维度。

能用本篇的同一道问题讲清这些区别，比记住 LangSmith 页面上有哪些按钮更重要。
