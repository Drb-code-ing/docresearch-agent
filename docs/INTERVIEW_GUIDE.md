## 3. 两分钟展开

“原先我有两类学习脚本，一类是用 LangGraph 学习查询拆分、混合召回，另一类是 Python 的 read/write 和 subagent。我没有简单把两份脚本拼接，而是找了一个共同目标：从资料到有出处的报告。

首版统一成 Python，用成熟的 BM25 库实现无服务依赖的检索，同时保留 Embedding 接口，用 RRF 融合不同检索通道。模型通过 Tool Calling 决定下一步，所有参数进入 Pydantic 校验。子代理只有 list/search/read 和结构化终止工具，没有 Shell、写文件和再次派发的权限。

每个子任务从新上下文开始，共享一个全局调用预算。默认最多两个子代理同时执行，超时或预算耗尽有明确状态。报告只允许引用实际返回过的片段 ID，同时保留原文快照、文件版本和行号。我也明确区分来源存在和结论正确，目前后者仍需要人工核对。

验证方面，我用确定性模型测试任务派发、工具回填、结果收集与报告生成，用 MockTransport 验证接口契约，并补了路径、非法参数、预算、超时、取消等测试。自编资料上的一次真实运行完成了两个子代理研究与最终报告，留下调用计数和轨迹。项目的价值是把执行边界做完整，而不是堆复杂框架或宣称生产规模。”

## 5. 关键追问与回答

这部分适合自问自答。要系统理解实现，先看后面的“第 9 节：逐模块实现与口述手册”，再回到这里模拟追问。

### Q1：为什么这算 Agent，而不只是工作流？

真实模式下下一步不是由固定代码决定。模型可以选择 search、read_source 或 task，再根据结果决定继续补查或完成。代码规定可执行动作和终止上限，模型在范围内决策。离线 Demo 是脚本化工作流，只验证这个协议，并不证明自主决策质量。

代码证据：`runtime.py::ResearchRun.loop`，`provider.py::DemoModel`。

### Q2：Agentic RAG 比普通 RAG 多了什么？

多了围绕检索结果的动作选择：拆分任务、改写查询、再次检索和回读来源。每个代理最多三次 search，避免无限补查。但我没有独立的充分性判定器，也没评测证明它比单次 RAG 更准，因此称它为可承载有界检索决策的运行时更准确。

追问“谁决定是否充分”：模型判断，程序只强制次数、参数和权限。

### Q3：为什么不继续用 LangGraph？

原学习代码使用过 LangGraph，这个项目选择显式循环，方便完整理解 messages、tool_call_id 和结果回填，也减少依赖。系统状态不多、无持久检查点和人工审批，直接循环足够。需要长任务恢复、持久状态图和人工中断时可以再评估 LangGraph，但不会为了简历关键词虚写框架。

### Q4：为什么不使用 ES + Milvus？

小样例下它们增加安装与运行成本。我的目标先证明任务链路与权限，所以用 BM25 和可选内存向量。代价是每次启动重新建索引、没有增量更新、大规模性能和数据库级过滤。未来数据规模和过滤需求明确后再迁移，不声称现在具有数据库能力。

### Q5：为什么关键词和向量结果不能直接加分？

BM25 和余弦分数尺度不同，直接加权容易让一边支配。RRF 用排名贡献 `1/(60+rank)` 融合，降低对分数校准的要求。同一个片段 ID 在两路命中会累加。代价是忽略原始分差，不保证比所有加权融合都好，参数仍应靠数据集验证。

### Q6：RRF 是 rerank 吗？

它可以改变候选顺序，但这里准确叫“多路排名融合”。没有用 query-document Cross-Encoder 或专用重排模型，所以不会把它包装成已经实现模型重排。

### Q7：BM25 为什么有负分，你怎么处理？

很小的语料里常见词的逆文档频率可能导致非正分。如果直接过滤正分会误删命中。代码先以词项交集排除完全不匹配的片段，再按 BM25 排名，平分时用稳定 ID。这个补丁是小语料策略，中文分词仍较粗，真实效果要评测。

### Q8：子代理的隔离到底隔离了什么？

隔离对话上下文和可用工具。每个 child 是新 messages，新 seen 集合；不会复制父代理的聊天。它们运行在同一个 Python 进程并共享 corpus、provider 和预算，所以不是文件系统隔离、进程隔离或容器沙箱。

### Q9：模型能不能要求子代理写文件？

提示不够，代码也会拦。child 的 Schema 清单没有写工具，dispatch 还会根据 parent 标记检查允许的工具，即使模型伪造调用名称也被拒绝。真正的文件发布只有主运行出口能触发。测试对 task、save_report、bash、write_file 的 child 调用都检查了拒绝行为。

### Q10：为何只读子代理，父代理统一写？

多个研究者并发写报告容易覆盖、冲突、留下半成品。只读研究负责提供结果，主代理负责统一格式，程序负责正式写入，能把并发写冲突和权限问题减到最少。它是权限分工，不是靠“请不要写”这类提示保证。

### Q11：怎样保证并发时预算不超？

共用 Budget，检查和计数之间没有 await，同一个 asyncio 事件循环不会在这几行代码中切换协程。计数在请求之前增加，失败也占额度。测试用四个并发请求争两次额度，验证仅两次成功预留。

这不适用于多线程或多进程共享计数；迁移到服务端多实例就需要外部原子存储或事务。

### Q12：为什么 semaphore 不等于完整任务队列？

Semaphore 只限制单进程同时进入执行区的 child 数量。它没有持久化、跨进程消费、重试队列或崩溃恢复。max_tasks 则控制总派发数，两个限制负责不同维度。

### Q13：`asyncio.gather` 中一个失败，其余怎么办？

默认 gather 不会按我需要的方式保证所有兄弟协程都结束，所以外层 finally 逐一 cancel 未完成 task，再 gather(return_exceptions=True) 等待取消完成。预算失败和总超时不会留下失控子任务。但远端服务收到的请求可能继续生成，这是网络与计费层无法由本地 cancel 保证的。

### Q14：总调用预算与 Token 预算有什么区别？

现在只限制请求次数，每次聊天设置输出上限，还统计返回的 chat usage。输入上下文没有按 token 做精确裁剪，也没有金额预留，不能称“费用预算”。Embedding 建索引也会用次数，可能占掉聊天额度；这个取舍写在 README。

### Q15：引用校验能防幻觉吗？

能防止随意引用不存在或未见过的片段，但不能证明结论被原文支持。模型可能拿真的片段支持假的结论。当前保存原文快照供人工核对，并在报告里提醒。下一步需要 claim-evidence 评测和人审，不能只再加一个模型就宣称绝对可靠。

### Q16：源文件改了，报告怎么追踪？

读取时保存内容快照，ID 与 SHA-256 版本绑定，任务内的 read_source 读快照而不是新文件。sources.json 保存被引用的正文，之后即使原文件变了，仍能核对当时版本。但这不是多文件同时点一致性快照。

### Q17：怎么防路径穿越和提示注入？

模型没有任意路径参数，只能用入库片段 ID；入库时 resolve 检查范围并忽略链接、隐藏内容，写入目录与资料目录分离。提示注入方面，指令里声明资料是数据，真正的权限控制则由工具白名单承担。

不能承诺完全免疫。模型仍可能被正文诱导生成错误报告；恶意本地进程替换路径的竞态也不是当前小工具能防住的。

### Q18：HTTP 200 就是调用成功吗？

不是。先检查状态码，再检查响应结构能否转换为 Reply/ToolCall。choices 为空、message 为空、工具参数格式错误等都有不同失败位置。兼容协议异常统一成 ProviderProtocolError，不把提供方正文和密钥写入日志。模拟传输测试覆盖这些场景。

### Q19：为什么会有 partial，而不是只有成功失败？

调研可能有可交付结论但缺关键资料，或部分子任务失败。把它标成 completed 会误导用户，把所有结果丢掉又浪费已有证据。因此保留报告并标 partial。completed 也只是执行完成，不是事实真实性背书。

### Q20：如何证明测试不是“mock 自己骗自己”？

我明确分层。文件、检索排序、Schema、权限、预算、取消这些确定性逻辑用自动化测试验证；HTTP Mock 验证传输契约；Demo 证明消息循环能串通；另外用自编资料完成了一次真实模型端到端验收。单次验收仍不是准确率评测，质量结论需要固定题目、标注与对照组。

### Q21：为什么没有做前端？

前端不是本次要补的核心能力。CLI 可以更快验证工具执行、证据与失败路径，已有其他项目展示前端经验。运行契约稳定后加 Web UI 才不会把漂亮页面覆盖在不可靠执行链上。简历因此没有写 FastAPI/React 是这个项目的技术栈。

### Q22：项目里你认为最值得讲的取舍？

“我没有保留原 Harness 的任意 Shell 黑名单，而是直接移除通用 Shell。项目任务只需要资料研究，给子代理读与检索就足够。权限减少，比不断修补危险命令匹配更容易验证。”

可以继续讲：为什么本地 BM25 先于 ES/Milvus；为什么报告统一写入；为什么先证明引用来源而不宣传彻底消除幻觉。

## 6. 一个能讲清楚的排错案例

审查发现兼容提供方可能 HTTP 200 但 `choices=[]` 或 `message=null`。最初代码直接索引，会变成 IndexError/AttributeError，最终只留下笼统 failed。

处理过程：明确正常响应契约，增加 ProviderProtocolError 包装形状异常，再用 MockTransport 构造异常响应测试。这个案例展示的是“协议成功不等于语义/结构成功”，不是生产线上发生的事故，不要包装成线上故障。

另一处改动是子代理不再只返回结论与 ID，而是同时回传引用正文，让父代理能看到用于综合的证据。最终仍然没有自动蕴含校验，所以文案也保持克制。

## 7. 面试官要求下一步优化时

按风险与收益排序：

1. 在已完成的真实提供方验收基础上扩充多题复测，记录模型、参数、资料版本和调用量。
2. 构建带正确证据与无答案标注的小题集，对比 BM25、混合检索、补查策略。
3. 增加上下文 token 预算和来源压缩，避免多任务证据导致输入变大。
4. 加内容哈希缓存与增量向量索引，再考虑专用 reranker。
5. 产品需要 Web 时再加入 FastAPI、鉴权、上传隔离、任务持久化与进度界面。

不建议第一句就回答“上 Kubernetes、Redis、微服务”。先说明现在数据规模、部署方式和故障风险，再选择工具。

## 9. 逐模块实现与口述手册

阅读每个模块时，按同一顺序练习：先说“解决什么问题”，再说“输入输出”，然后说“核心实现”，最后说“为什么这样做”。不要一上来报文件名或框架名。

### 模块 A：CLI 与运行装配

**负责什么：** 把用户的目录、问题、运行模式和预算转换为一次研究任务。CLI 不承担研究决策。

**输入与输出：** 输入是命令行参数与显式环境变量；输出是状态、产物目录和统计 JSON，以及一个退出码。

**实现步骤：**

1. `argparse` 建立 demo/run 两个子命令，公共参数是 corpus、output、max-calls、timeout。
2. 创建 Corpus 完成输入检查；创建 Limits 做配置范围检查。
3. demo 注入 DemoModel；run 从环境变量创建 CompatibleModel，可选注入 embed 函数。
4. `asyncio.run()` 驱动 ResearchRun.run()，外层 finally 关闭 HTTP 客户端。
5. completed/partial 返回 0，失败状态返回 1；Ctrl+C 返回 130。

**为什么这样做：** 把“构造依赖”和“执行研究”分开，测试可以直接注入模拟模型，不用改 CLI 或去读真实密钥。

**面试怎么说：** “入口只负责参数和资源生命周期，研究逻辑放在 ResearchRun。我把模型作为依赖注入，所以同一套执行逻辑既能接真实接口，也能接确定性 fixture，测试不需要请求真实 API。”

**容易追问：** 为什么 partial 也是 0？因为有可交付产物，严格任务应再检查 run.json；退出码不能替代业务状态。为什么不自动读 .env？减少不经意使用旧凭据，真实模式要求显式配置。

### 模块 B：资料快照、分块与证据身份

**负责什么：** 把不稳定的本地文件变成一次任务内稳定、可定位的证据对象。

**核心数据：** Source 包含 id、相对 path、start_line、end_line、version、text；documents 只保留文件级元数据，sources 是 ID 到片段对象的字典。

**实现步骤：**

1. 根目录 resolve(strict=True)，验证是目录。
2. os.walk 不跟随目录链接，跳过隐藏目录、隐藏文件、链接与不支持扩展名。
3. 最多读单文件上限加一字节，超限直接拒绝；同时累计文件数、总字节数。
4. UTF-8 解码，计算完整文件 SHA-256；按完整行累积到字符上限后分块。
5. 以“相对路径 + 版本 + 行号 + 正文”计算片段 ID，并保存在内存。
6. 研究过程中按 ID 返回快照，最终将被引用的快照写入 sources.json。

**为什么这样做：** 光有文件名不能定位依据，光有行号不能识别文件被修改。版本和原文快照一起保存，才能回看“当时依据是什么”。

**面试怎么说：** “我不是每次检索后再去读最新文件，而是任务开始先建立有上限的快照。引用带相对路径、行号和内容版本，后续读到的始终是同一份快照，避免检索和报告对应不同文件版本。”

**容易追问：** 为什么不做 overlap？这里按行分块选择简单可追踪，跨块语义可能丢失；可以按标题/段落并加重叠改进，但需要保持精确来源映射。为什么 1800？是工程上限，不是已评测的最优 chunk size。

### 模块 C：BM25、向量召回和 RRF

**负责什么：** 把自然语言问题变成少量候选原文，而不是把所有资料塞入上下文。

**输入与输出：** query + limit -> Source 列表。prepare() 负责可选向量索引初始化，search() 负责在线查询。

**实现步骤：**

1. tokenize 提取英文词、数字/下划线词和中文字，再加中文相邻双字词。
2. 以成熟 rank-bm25 库建立语料统计；查询时先保留有词项交集的候选，再按分数取前 20。
3. 启用 embedding 时，分批把片段送给接口，检查数量、维度、NaN/Inf 与零范数，再 L2 归一化。
4. 查询也转成向量，与片段矩阵做点积，得到余弦排序候选。
5. 两路以统一 ID 聚合 RRF 得分，排序后取用户请求的前 k 个。

**举例理解 RRF：** A 在关键词第 1、向量第 3；B 仅在向量第 1。A 得分 `1/61 + 1/63`，B 得分 `1/61`，因此两路都支持的 A 更靠前。它不是把 BM25 的 9.3 和余弦的 0.8 直接相加。

**面试怎么说：** “我用 BM25 保留术语匹配，用可选 Embedding 覆盖语义表达差异。融合选择 RRF 是为了不直接混加不同尺度分数。索引只保留在内存，适合这个小型资料工具，不能说具备向量数据库的大规模服务能力。”

**容易追问：** 召回和生成谁保证答案正确？检索只给候选，不保证结论；0.1 的余弦是不是可靠？不是，正值过滤只是候选规则，不是校准置信度。真实向量接口验收是否成功？按 VALIDATION 的具体证据回答，不混同合成向量单元测试。

### 模块 D：模型传输与 Tool Calling 契约

**负责什么：** 把 Python messages/tools 变成 HTTP 请求，把不可信的提供方响应变成内部 Reply。

**关键对象：** Reply 包含 content、ToolCall 列表和 usage；ToolCall 有 id、name、arguments。每个具体工具由 Pydantic Contract 描述，禁止额外字段并启用 strict 类型校验。

**实现步骤：**

1. tools_for 根据角色生成工具 Schema，发送至 `/chat/completions`。
2. HTTP 状态错误先抛出；HTTP 200 也要能提取合法 message/tool_calls。
3. 构造 Reply/ToolCall，结构异常转换为 ProviderProtocolError。
4. 调度时再按工具名称选择更具体的 Schema，例如 Search、Task、ReadSource。
5. 参数错误作为 tool 结果回填，给模型有限机会修正，而不是执行未验证参数。

**为什么有两层校验：** Reply 校验“这是不是一个合法工具调用”，Search 等校验“这个工具参数是否符合业务要求”。把 JSON 解析成功当作校验成功是不够的。

**面试怎么说：** “工具的 JSON Schema 是给模型看的提示，Pydantic 是执行前真正的门禁。模型可能生成多余字段、把数字写成字符串，或伪造工具名，代码仍要重新检查，不能只信模型遵守 Schema。”

**容易追问：** JSON Mode 与 Tool Calling 有什么区别？前者约束文本格式，后者通过明确的函数名和调用 ID 表达动作请求；无论哪种都需要执行端验证。structured output 是否等于正确事实？不等于，只约束形状。

### 模块 E：主代理循环与有界检索决策

**负责什么：** 在“模型请求动作”和“程序执行动作”之间持续迭代，直到结构化结束或达到上限。

**内部状态：** messages 负责模型上下文；AgentState 负责角色、已见证据集合和 search 次数；Budget 是所有代理共享的调用约束。这三者不要混为一谈。

**实现步骤：**

1. 新建 system/user 两条消息，选定角色可见工具和最大步数。
2. 预留调用次数，再请求模型。
3. 普通文本没有产生正式报告，提醒模型使用终止工具，并消耗一次循环步数。
4. 对 tool calls 检查 ID 唯一性，把 assistant 请求放入 messages。
5. 普通工具执行后，用原 tool_call_id 回填工具结果。
6. 终止工具只能单独调用，解析 Report/ResearchResult 并校验引用。
7. 所有循环都受步数上限限制；单代理 search 还单独限制为 3 次。

**为什么不能只判断模型说“完成了”：** 普通自然语言没有明确可验证字段，也可能在错误后提前结束。终止工具给了代码一个稳定完成信号。

**面试怎么说：** “我的 Agent 循环没有把自由文本当作正式完成。它必须用结构化终止工具提交发现和引用，程序校验通过才接受。检索不足可以改写，但每个 Agent 有三次检索上限和步数限制，模型不会控制无上限 while True。”

**容易追问：** 三次用完怎么办？返回已有证据和明确缺口；没有自动更换模型或继续无限补查。怎么判断问题复杂？真实模型决定是否 task，没有独立训练的路由器。

### 模块 F：子代理派发、上下文和并发

**负责什么：** 让独立研究维度分工完成，并控制父上下文增长和权限范围。

**实现步骤：**

1. 父代理发出一个或多个 task(question)。
2. child 在 await 前检查 max_tasks 并占用名额，创建独立 AgentState。
3. 进入 semaphore，活跃 child 计数加一。
4. 为子问题新建 messages，复用同一个 loop，但只暴露只读工具与 finish_research。
5. 校验子结果的引用确实在它自己的 seen 中。
6. 将 findings/gaps/被引用正文回传父代理，并登记父代理可以使用的引用。
7. 无论成功失败都在 finally 减少活跃数；特定子失败转成结构化状态。

**为什么不是每个小步骤都派一个 Agent：** 多 Agent 会增加请求开销、重复检索和汇总成本。只有独立研究面适合拆；简单问题由主代理直接完成更省。

**面试怎么说：** “我的子代理不是多个角色提示词同时聊天，而是一次带权限的独立上下文调用。父代理只交任务，子代理自行检索并提交证据；代码限制最多两个并发、最多四个任务，且不允许 child 递归派发或写文件。”

**容易追问：** 共享什么，不共享什么？共享快照、提供方、Budget，不共享对话历史和 seen。子代理失败就全部失败吗？局部失败可回传父代理并生成 partial，全局预算耗尽会结束整个运行。

### 模块 G：预算、超时和失败收敛

**负责什么：** 把不确定的模型行为限制在可接受资源内，并让失败有明确结果。

**实现步骤：**

1. Budget 在任何 await 前检查并递增 calls，Embedding 与聊天共用这条路径。
2. dispatch 和有效终止尝试计数 tools；max_tools 防止工具调用膨胀。
3. 单次 await 包裹 request timeout，整个研究区间包裹 run timeout。
4. 同批工具用任务列表 + gather；finally 取消尚未结束的兄弟任务并等待它们退出。
5. run 把异常映射到 budget_exhausted/timeout/failed，生成可定位的元数据。

**面试怎么说：** “我把请求次数、循环步数、检索次数、子任务数、并发和时间当成不同维度分别限制。它们不能互相替代：限制两并发并不能防止串行派发一千个任务。错误后还要把子任务取消并等待结束，不能只是父函数 return。”

**容易追问：** 这是线程安全的吗？是单事件循环内的协作并发计数，不是跨线程保证。timeout 会不会退费？不能保证远端停止。为什么没有自动重试？重试会放大成本，真实策略应区分 429/5xx/协议错误并重新消耗预算，不简单无限重试。

### 模块 H：引用校验和报告发布

**负责什么：** 将模型返回的建议变成有出处、不会覆盖资料的正式产物。

**实现步骤：**

1. 每个 finding 必须含至少一个 source_id，整体至少有 findings 或 gaps。
2. 所有引用必须在当前代理 seen 内，未知或未读 ID 会被拒绝。
3. 主结果携带 gap 或存在 child failure 时标 partial，否则 completed。
4. 收集报告真正引用的 Source，按稳定顺序生成编号与来源列表。
5. 生成 report.md、sources.json、trace.json、run.json。
6. 随机 run_id 新目录拒绝复用；固定文件名同目录临时写入后 replace。

**面试怎么说：** “我把引用存在性和结论正确性拆开处理。程序保证引用来自本次读取的资料，并保存当时的版本与原文；它不声称自动证明语义正确。正式写入只有统一出口，模型不能传任意路径，源目录与报告目录也不能重叠。”

**容易追问：** 原子写是不是四文件事务？不是，只保证单文件替换，异常可能留下部分目录。report.md 能安全当 HTML 执行吗？不能，报告是模型输出的 Markdown，查看器仍应按不可信内容处理。

### 模块 I：测试、观测和证据层级

**负责什么：** 让重要行为有自动化证据，并能从运行产物解释发生了什么。

**实现方式：** 临时 corpus 测试文件策略；合成 embedding 测排序契约；注入常量/慢模型触发错误与取消；MockTransport 测 HTTP 请求和响应；Demo 跑全部执行链；真实样例验收确认选定模型确实发出工具调用并生成报告。

trace 不保存完整聊天，仅有阶段、代理名、工具名、时间和错误类别。run.json 汇总调用数、usage 和并发峰值。它们方便排错，但不是跨进程可恢复状态，也不能完全重放原模型输出。

**面试怎么说：** “我没有把所有验证压成一句测试通过。确定性逻辑由 pytest 验证，协议由 MockTransport 验证，真实提供方只在授权的自编资料上验收。运行轨迹可以说明它实际派了几个任务、何时检索、何时结束；真实质量还需要标注题集和对照组。”

**容易追问：** 最值得补的测试是什么？真实资料上的证据支持率、无答案识别、跨文档问题与成本比较；同时补并发本地文件攻击模型或服务端隔离，要先改变系统部署假设。

## 10. 五分钟完整讲述模板

按下面顺序说，不要一次把所有细节堆给面试官：

1. **场景 30 秒：** 用户有多份资料，需要生成可核对报告，普通问答不够，通用 Shell 又权限过大。
2. **总体链路 45 秒：** CLI -> 文件快照 -> 检索 -> 主/子 Tool Calling -> 引用校验 -> 报告；指出模型与程序的分工。
3. **重点模块 90 秒：** 子代理上下文和工具隔离、共享预算、有界并发。它们最直接体现 Agent 工程理解。
4. **检索证据 60 秒：** BM25/向量为什么互补，RRF 为什么不用原始分数，版本与来源如何关联。
5. **验证和取舍 45 秒：** 展示自动化、CI、一次真实运行证据，解释不等同于准确率或生产规模。
6. **追问入口 30 秒：** “这里我花时间最多的是权限、取消和引用边界，可以进一步展开。”随后根据面试官问题进入对应模块。

不要刻意把所有答案背到五分钟。应能在 30 秒、2 分钟、5 分钟之间缩放，核心链路不变，细节随追问展开。
