# DocResearch：详细项目理解文档

本文按完整项目的运行顺序展开，不按开发阶段记录。阅读目标是：能独立说明每个模块的输入、内部处理、输出，以及它为什么需要存在。开发时间线单独放在 `DELIVERY.md`。

## 1. 先建立一个最小心智模型

把这个项目理解成“有权限和次数限制的资料研究员”，而不是一个万能聊天机器人。

用户给一个研究问题和一个资料目录。主代理决定直接检索，或者把不同研究维度交给子代理。每个子代理只读资料，把发现和证据交回。主代理汇总后提交结构化报告，由 Python 程序校验和落盘。

真正负责读文件、计数、判断权限和写报告的是代码。模型只能提出工具调用，不能绕开工具权限直接执行 Shell。这个分工就是项目的核心。

最小链路：

```text
CLI 参数
  -> Corpus：读取有上限的资料快照
  -> Retriever：BM25 / 可选混合检索
  -> 主代理 Tool Calling 循环
     -> 自己 search/read_source
     -> task：子代理独立研究 -> findings + gaps + sources
  -> save_report：结构校验 + 引用校验
  -> report.md + sources.json + trace.json + run.json
```

`save_report` 的名字是模型可见命令。它并不立即写文件，而是先返回已验证的 `Report`，由最外层 `ResearchRun.run()` 统一生成产物，减少写操作散落在工具分支里的风险。

## 2. 为什么做这个项目

原学习内容有两条线：

1. JavaScript Agentic RAG：查询路由、问题拆分、多路召回、重排。
2. Python Harness：模型回复 -> 工具调用 -> 工具结果 -> 再请求模型，以及新上下文的子代理。

如果只拼接两个脚本，依然没有完整产品目标。本项目选择“本地资料调研并生成可追溯报告”，让每项能力都有职责：检索定位内容、读取获得原文、子代理分工、文件写入形成可交付结果。

它与更完整的业务平台不同：不做用户登录、业务数据库、任务队列或 Web 前端，而是突出 Agent 执行机制和可验证的工程边界。

项目刻意没有照搬 ES/Milvus。它们属于原学习代码中的经验，不是这里的运行依赖。为了让别人克隆后直接运行，这里使用成熟的 `rank-bm25` 库，可选提供方 Embedding 与 NumPy 余弦计算。不是重新手写 BM25 算法，也没有把关键词匹配冒充向量检索。

## 4. 一次任务怎样流转

### 4.1 启动与索引

`execute()` 创建 `Corpus`，选择 `DemoModel` 或 `CompatibleModel`，然后创建单次使用的 `ResearchRun`。一个实例不能重复运行，避免上一次的计数、证据和错误进入下一次任务。

Corpus 只接收 UTF-8 Markdown/TXT。它忽略隐藏文件、隐藏目录和符号链接，限制最多 100 个文件、单文件 256 KB、总计 2 MB、最多 400 个片段。单行上限是 1800 个字符，超过就拒绝，要求先整理资料；它与下文约 1800 字符的分块目标是两个检查。这是明确可控的输入契约，而不是通用文档解析能力。

按完整行累计到约 1800 字符分块，不跨行切半。片段记录路径、起止行号、文件 SHA-256 和片段 ID。片段 ID由相对路径、文件版本、行号及正文共同计算，因此修改源文件后，新快照不会错误复用旧 ID。

任务期间 `read_source` 返回内存快照，不重新打开随时可能变化的源文件。这样报告引用与检索所见是同一版本。它不保证跨文件快照在同一瞬间取得，也没有数据库事务意义上的快照隔离。

### 4.2 模型先拿到什么

主代理最开始只有系统规则和用户问题，以及工具 JSON Schema。它不会一开始看到所有文档全文。

系统规则说明资料是不可信数据，不能把资料内的指令当作用户指令。这是模型层提示，不是对提示注入的完美防护。更重要的是代码层没有暴露通用 Shell、源文件写入、任意网络请求等工具。

### 4.3 Tool Calling 的循环

`loop()` 每一步调用 `model.chat(messages, tools)`。其中 list_documents 只列举允许的文件名与版本，不返回所有全文；search 定位原文片段，read_source 按片段 ID 读取正文，task 派发子任务。

- 模型返回普通文本：代码把文本加到上下文，并要求使用终止工具完成。
- 返回普通工具调用：先校验工具是否属于当前角色，再按 Pydantic Schema 解析参数，执行并把结果作为 `role=tool` 回填。
- 返回终止工具：要求它单独出现，校验结果与引用后结束循环。
- 达到步数上限还未完成：抛出 `StepLimit`，最终状态为 `failed`，保留诊断产物，不伪造报告。

每条工具结果都使用原来的 `tool_call_id`，维持模型协议。重复 ID 会被拒绝；未知工具、额外字段和错误参数类型会得到受控错误，模型可以在剩余步数内修正。

### 4.4 怎样派发子代理

父代理调用 `task(question)`。程序创建新 `AgentState` 和新 messages，只传当前子问题。子代理不继承父代理完整聊天历史，也没有 `task` 或 `save_report` 工具。

它能 list/search/read，最后调用 `finish_research` 返回：

```json
{
  "findings": [{"statement": "一个待核对的发现", "source_ids": ["实际读取的片段ID"]}],
  "gaps": ["尚无同条件性能数据"]
}
```

结构示例中的 ID 是说明文字，实际格式要求 16 位小写十六进制。成功时父代理还会收到被引用的原文 payload，而不仅是编号。

不同 tool calls 可同时启动，子代理执行由 `asyncio.Semaphore` 限制，默认最多 2 个。创建的任务总数最多 4 个，子代理不能递归派发。这里是单进程协作式并发，不是多进程隔离，更不是分布式任务系统。

依赖前一个结论的问题不能盲目并行。系统提示要求等待先前证据后再派发后续问题，但目前没有 DAG 调度器来强制检查问题的语义依赖。

## 5. 检索为什么这样设计

### 5.1 BM25 的位置

BM25 适合术语、型号、函数名等字面信息。英文按词切分，中文采用单字和相邻双字词，避免引入大型分词模型。代价是中文语义与边界识别较粗糙。

小语料的 BM25 分数可能为零或负值，所以代码没有简单采用 `score > 0` 过滤，而是先判断查询词与片段是否有词项交集，再按 BM25 分数排序。分数相同时用片段 ID 保证结果可复现。这个设计针对小规模样例，不代表完成了检索质量调参。

### 5.2 可选语义检索

设置 Embedding 模型后，`prepare()` 每批最多 32 个片段请求向量。向量必须二维、数量一致、维度一致、有限且范数非零，再做归一化。查询向量同样校验，通过点积获得余弦相似度。

关键词和向量各保留最多 20 个候选。向量通道只保留正相似度，它是简单候选过滤，**不是已校准的证据充分性阈值**。每次执行重建内存索引，因此大资料量会重复消耗 Embedding 调用；该成本计入总调用数。

### 5.3 RRF 融合

两路分数不在同一尺度：BM25 原始分数不能直接和余弦值相加。RRF 使用排名：

```text
score(document) = sum(1 / (60 + rank_in_channel))
```

同一片段在两路出现会累加，天然按统一 ID 去重。60 是常用平滑参数，这里固定使用，尚未通过实际评测寻优。

RRF 是排序融合，不是 Cross-Encoder 或专用 rerank 模型。简历可以写 BM25/向量/RRF 接口，不能写“已接入生产重排服务”或“召回率提升 X%”。向量路径的单元测试使用合成向量，真实接口验收范围见 `VALIDATION.md`，它不等于标注数据集上的质量评测。

### 5.4 Agentic 在哪里

固定 RAG 通常检索一次再回答。本项目的模型可以决定是否派发、使用哪个查询、是否回读来源、检索不足时怎样改写。每个代理最多 3 次 search，足以演示有限的补查。

项目没有独立的证据充分性分类器或自动评分器。“是否还需要补查”由模型判断；提示与工具次数限制提供执行框架，不能声称已经证明它会比固定链路更准确。离线 Demo 更不会验证智能决策，因为其工具调用顺序是确定的。

## 6. 预算、失败与取消

默认限制：24 次聊天/Embedding 请求、48 次普通工具与有效终止尝试、主代理 8 步、子代理 5 步、最多 4 个子任务、并发 2、单请求 30 秒、任务 180 秒。

`Budget.invoke()` 在 await 前检查并加一。所有代理与 Embedding 共用同一个 Budget，单事件循环中这段代码不会在检查和递增之间让出执行权，所以不会因协作并发超额预留。失败请求也占次数，不做失败返还。

这不是费用预算。单次聊天请求设置最多 1600 个输出 token，输入上下文仅通过资料规模、片段数与步数间接限制；没有严格上下文 token 裁剪，也没有总 token/金额预留机制。工具错误计数也不等于审计日志中每个事件的数量，日志用于定位阶段而非逐笔收费结算。

同批工具通过 `gather` 等待。它外面有 `finally`，取消仍未结束的任务，并再次 gather 等待它们结束，避免主任务失败后子任务继续偷偷运行。外层 `asyncio.timeout` 覆盖 Retriever.prepare 的向量索引准备及 Agent 循环；单请求 timeout 负责慢提供方。CLI 在 run 之前构建 Corpus 的磁盘加载，以及结束后的文件发布，不包含在运行期 timeout 里。

取消本地 HTTP await 不保证远端模型已经停止生成或停止计费。文件处理是有界同步操作，也不是可强杀的独立进程。

| 状态 | 含义 | 报告 |
| --- | --- | --- |
| completed | 模型完成结构化结果，未报告缺口且没有子任务失败 | 有 |
| partial | 有可交付报告，但存在缺口或子任务失败 | 有 |
| budget_exhausted | 调用/工具总预算耗尽 | 无，仅诊断 |
| timeout | 任务或未被子任务吸收的请求超时 | 无，仅诊断 |
| failed | 协议、步数或其他运行失败 | 无，仅诊断 |

子任务超时会成为子任务失败结果，父代理可能继续生成 partial 报告；总调用预算耗尽则向上传播并终止。达到任务数上限会拒绝新增派发，不冒充成功。

`completed` 不等于内容真实、没有遗漏或达到质量门槛，它只是执行协议状态。Ctrl+C 返回 130，不保证最后的诊断产物已写出。启动参数错误、空资料、输出写失败也可能只打印错误类别，不留下运行目录。

## 7. 引用校验到底保证什么

每个 AgentState 有独立的 `seen` 集合。search/read 返回了原文才把 ID 加入集合。子代理终止时引用必须在自己的 seen 中；父代理收到成功子任务的结果和原文后才获得这些引用 ID。

`validate_evidence()` 检查引用是否来自当前证据集合，也要求至少有一个发现或一个明确缺口。它不检查“这个结论是否真的被这段文本蕴含”。

例如原文说“尚无性能数据”，模型写“性能提升 50%”并引用该段，ID 校验仍可能通过。因此报告明确提醒人工核对，不能宣传“消除幻觉”。进一步完善可以加入基于原文的 claim-evidence 审核、人审标注和有对照组的评测。

`sources.json` 存被引用的原文快照，便于之后离线核对。它含用户资料正文，和 reports 目录一起默认不提交 Git。Trace 只存阶段、计数、错误类别，不记录密钥、完整提示或完整模型对话。它不是可精确重放模型响应的事件日志。

## 8. 文件权限与安全边界

模型没有任意路径读取参数，只能访问已经入库的片段 ID。程序还通过 resolve 后的相对路径检查、拒绝符号链接、文件类型和规模限制控制输入。

报告与资料必须是互不包含的目录树。运行 ID 由程序生成；输出文件名固定四种。每个文件在同目录临时写入后 replace，已有运行目录拒绝复用。这是单文件原子替换，不是四个文件的事务，磁盘故障可能留下部分产物。

这些措施针对可信本地用户运行的小工具。恶意本地进程并发改换目录、符号链接的 TOCTOU、操作系统访问控制、多租户隔离均不在保证范围内。不能说“有安全沙箱”，更不能在未加鉴权隔离时把 CLI 直接包装成公网服务。

原学习脚本有 `shell=True` 和危险词黑名单；本项目选择不迁移通用 Shell，而不是继续扩展黑名单。这是在小项目中降低权限面最有效的决定。

## 9. 怎么验证，而不是只说做完了

运行：`uv run ruff check .`、`uv run ruff format --check .`、`uv run pytest -q`、`uv run docresearch demo`。

目前本地 51 项测试通过，CI 在 Windows/Linux、Python 3.11/3.12 上执行相同检查。来源符号链接测试在不允许创建链接的机器上会 skip；需要观察实际 CI 日志，不应把 skip 写成已覆盖。

测试分四层：

1. 文件层：稳定 ID、内容版本、行号、快照不漂移、越界路径、输入上限、拒绝覆盖。
2. 检索层：中英文 token、命中/不命中、合成向量混合召回、非法维度、NaN/Inf/零向量。
3. 运行层：端到端演示、上下文独立、子代理权限、总预算、并发、超时取消、错误终止结果。
4. 提供方层：HTTP MockTransport 检查请求契约，模拟成功响应、HTTP 错误、异常 JSON 结构。

最后一层不是对外发起真实请求。另有一次使用自编样例的受控真实调用验收：主代理派发两个研究子代理，经检索和回读后生成引用报告。验收数据、模型标识和局限放在 `VALIDATION.md`，一次运行不能代表平均性能或质量评测。

开展质量评测时，需要记录模型、时间、参数、输入版本、实际 usage 和结果，再构建标注题集，对比 BM25、混合检索、Agent 补查的质量和成本，不能只展示一个看起来成功的答案。

## 10. 可练习的修改顺序

1. 加一份自己的非敏感 Markdown，先观察 chunk ID、行号和关键词召回变化。
2. 修改 DemoModel 的两个子问题，确认它是协议 fixture，不是自然语言智能。
3. 将 concurrency 从 2 改成 1，观察 trace 与 peak_child_concurrency，理解并发限制。
4. 将 max_calls 降为 1，观察为什么没有报告而只留下诊断文件。
5. 配置真实模型，仅用自编样例验证 Tool Calling 兼容性。
6. 再配置 Embedding，解释为何建索引也会用掉总调用预算。
7. 完成标注评测后，再考虑专用 reranker、持久索引、Web 页面和严格 token 预算。

不要先堆前端、队列和数据库，再回头寻找 Agent 有什么用。这个项目最值得掌握的是：不可信模型输出如何被转换为有类型、有限权、有终止条件、能留下证据的程序行为。

## 11. 把对象串起来：完整请求的逐步展开

### 11.1 先分清六种数据

| 数据 | 由谁产生 | 谁消费 | 用途 |
| --- | --- | --- | --- |
| Source | Corpus | Retriever、工具、报告渲染 | 一段带版本与行号的原文 |
| messages | loop | Model.chat | 单个代理可见的对话上下文 |
| ToolCall | 模型响应经校验 | dispatch / loop | 一个待执行动作，不是已经完成的操作 |
| AgentState | 主运行/child | 权限及引用校验 | 角色、seen、检索次数 |
| ResearchResult / Report | 模型终止工具经校验 | 父代理 / run | 发现、引用、缺口，Report 额外有标题 |
| RunOutcome | run | CLI | 状态、产物目录、运行统计 |

`messages` 不等于 AgentState。前者给模型看，后者由程序维护。模型在文本里声称“我读过某文件”，不会自动改变 seen；只有程序真正执行过读取/检索才改变它。

### 11.2 从一个 search 调用看完整消息协议

初始上下文为系统消息和用户问题。模型返回的工具请求形状如下，省略其他响应字段：

```json
{
  "id": "call_001",
  "type": "function",
  "function": {"name": "search", "arguments": "{\"query\":\"pgvector 部署\",\"limit\":2}"}
}
```

注意 arguments 是 JSON 字符串，不是已经验证过的 Python dict。运行时通过 `Search.model_validate_json()` 将它变成强类型对象，再调用 `Retriever.search`。

程序必须把这次 assistant 的 tool_calls 加入 messages，再追加带同一个 `tool_call_id` 的 tool 消息。否则提供方无法知道结果对应哪次调用，可能直接报协议错误。

```text
messages[0] system: 工具规则与证据规则
messages[1] user: 调研问题
messages[2] assistant: tool_calls=[search(call_001)]
messages[3] tool: tool_call_id=call_001, content={sources:[...]}
messages[4] assistant: 决定补查、回读或结束
```

Tool 结果的 sources 已含原文、路径和行号。对于需要重新明确查看的片段，模型可以调用 read_source，它只拿一个受控 ID，不接受硬盘绝对路径。

### 11.3 task 怎样复用同一套循环

task 分支没有另一套完全独立的 Agent 实现，它调用 `child()`，child 创建新状态后复用 `loop()`。区别由 `parent` 标记决定：

```text
parent=True  -> 工具含 task / save_report，最多 parent_steps
parent=False -> 工具含 finish_research，最多 child_steps
```

因此，主从代理共用工具协议、参数校验、调用预算与错误处理，不需要复制一份 while 循环。子代理收敛后返回结构化对象，父代理把它当作 task 工具结果继续自己的循环。

不要把这里的“子代理”理解成一个持续运行的后台服务。它是一个拥有新上下文和受限能力的异步函数调用，由主任务负责等待和取消。

### 11.4 实际真实调用的时间线

受控样例的 trace 展现了以下顺序，数据来自一次运行，不是写死的流程：

1. 主代理第 1 次请求同时产生 list_documents 和两个 task。
2. 两个 child 分别先列举资料，再各发起两次 search。
3. 两个 child 根据结果调用 read_source，核对相关片段。
4. research-2 在自己的第 4 步完成，research-1 也在第 4 步完成。
5. 父代理收到两份结果及引用原文，第 2 次请求生成 save_report。
6. 程序校验 7 个发现与 8 个缺口，渲染报告及三个 JSON 文件。

总计 10 次聊天请求、15 次计数工具调用、并发峰值 2。状态为 partial 的原因是报告主动保留了性能基准等资料缺口，而不是子代理运行失败。

### 11.5 报告写入不是让模型生成任意文件

模型提交结构化 Report：标题、发现、引用 ID 和缺口。Python 的 render 负责标题、编号、章节和来源列表；文件名与运行目录也由程序决定。模型不能把输出位置改成用户源文件。

渲染会转义 HTML 字符，但输出仍是模型产生的 Markdown，应当按不可信内容查看。没有浏览器页面自动执行它，也没有声称提供完整 Markdown 安全渲染器。

这说明“模型负责内容建议，程序负责结构和副作用”的分工不是一句口号，而是代码入口决定的。

## 12. 模块之间的依赖为什么没有继续拆碎

Corpus 集中处理路径、上限、分块和版本，外部只需要读 sources/read；Retriever 集中处理两个通道及融合，外部只调用 prepare/search；ResearchRun 对外只暴露 run，内部自己协调预算、工具、子代理和输出。

Model 使用小型协议抽象，是因为确实有 CompatibleModel 和 DemoModel 两种实现，测试也能放入 ConstantModel/SlowChildren。这是已有真实替换需求，而不是为了展示设计模式。

Embedding 通过可调用对象注入，Retriever 不需要知道 API key、base URL 或 HTTP 客户端。Budget 包装这个调用，就能把 Embedding 也纳入共享预算。这比在每个检索分支手写请求计数更集中。

文件写入保持在 ArtifactWriter，模型请求保持在 provider，检索算法保持在 retrieval。将来修改提供方协议不应该改路径安全，将来改分块策略不应该改 Tool Calling 协议。这是理解整个项目最重要的模块分工。
